The problem

Which molecules in my library look like this one?

Each molecule is turned into a fingerprint: a 2,048-bit pattern recording the small structural pieces it contains. Two molecules are compared with the Tanimoto score, shared bits divided by total distinct bits, from 0 (nothing in common) to 1 (identical fingerprints).

An exact search compares the query with every molecule in the library, so cost grows with library size. Real libraries hold millions to billions of molecules, which is why even small per-comparison savings matter. This project tests two published ideas for making that search faster without changing a single result.

Idea 1 · skip what can't match

The bound can only skip molecules far from the query's size

Swamidass & Baldi (2007) showed that a fingerprint with a bits set can never score higher than min(a,b)/max(a,b) against one with b bits set. So for a threshold t, any molecule with fewer than t·a or more than a/t bits is skipped without computing anything.

The catch: drug-like molecules are all roughly the same size, so their bit counts sit in a narrow band around bits. The window the bound must keep swallows almost all of that band until the threshold is very high. Move your cursor across the chart below: wherever it points becomes the query molecule's size.

Idea 2 · make each comparison cheaper

Packed bits are faster at every threshold; pruning only helps near 1.0

If skipping doesn't work, make every comparison faster. Each fingerprint is packed into 32 × 64-bit words in one contiguous array, and the whole library is scored in one vectorised pass: bitwise AND, hardware popcount, divide. This follows Dalke (2019), who argued that modern exact search is limited mainly by how fast memory can be streamed, not by arithmetic.

Side finding

Memory layout alone cost

RDKit keeps each fingerprint as its own object in memory. When the list of fingerprints was in a different order from the one they were created in (after shuffling or sorting), the same RDKit call on the same data took per query instead of . An early benchmark run hit exactly this and made the baseline look slower than it is. Every RDKit number on this page now uses fresh copies laid out in scan order, so the baseline is shown at its best.

    1. Rogers & Hahn (2010). Extended-connectivity fingerprints. J. Chem. Inf. Model. 50(5), 742–754. The fingerprints used (Morgan, radius 2).
    2. Bajusz, Rácz & Héberger (2015). Why is Tanimoto index an appropriate choice for fingerprint-based similarity calculations? J. Cheminform. 7, 20. Supports Tanimoto as the default metric.
    3. Swamidass & Baldi (2007). Bounds and algorithms for fast exact searches of chemical fingerprints in linear and sublinear time. J. Chem. Inf. Model. 47(2), 302–317. Source of the bound in idea 1.
    4. Dalke (2019). The chemfp project. J. Cheminform. 11, 76. Argues exact search is memory-bandwidth bound; motivates idea 2 and explains the side finding.
    5. Gómez-Bombarelli et al. (2018). Automatic chemical design using a data-driven continuous representation of molecules. ACS Cent. Sci. 4(2), 268–276. Source of the 250k ZINC subset.

    Prototyped in about a day with a coding agent (Claude Code). I chose the question and the comparisons; the agent drafted the code; nothing was reported until it matched a deliberately slow reference implementation. Two early runs gave misleading baselines (Python dictionary overhead, then scattered memory layout); both were traced and fixed, and the second became the side finding.
